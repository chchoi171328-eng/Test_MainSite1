# 성공사례 정적 전환 지시서 (Claude Code용)

> 결정: 성공사례를 Supabase에서 **가이드와 같은 파일 기반(정적)**으로 전환한다.
> 근거: 영구 문서 성격 + 판결문 PDF의 Base64 DB 저장 해소(CDN 캐싱·직접 URL) +
> 발행 파이프라인을 가이드와 통일(산출 폴더 복사 = 발행).
> 이 지시서는 **구조 전환과 기존 데이터 마이그레이션까지만** 다룬다. 신규 사례
> 생산은 success-case-writer 스킬(파일 기반 개정판)이 담당한다.
> 시각 정본: `case-detail-preview.html` (요약 카드·단계 라벨·결과 박스·유의점·
> **문서 카드** 포함 — 이전 CASE_DETAIL_BRIEF.md는 이 지시서로 대체됨).

## [작업 1] 콘텐츠 구조

```
/content/cases/{slug}/
├── index.md              ← frontmatter + HTML 본문
└── judgment-masked.pdf   ← 마스킹 판결문 (없는 사례는 생략)
```

frontmatter 스키마:
```yaml
title: "도로교통법위반(음주측정거부) 기소유예 처분 사례"   # 상세 페이지·SEO 제목
list_title: "음주측정거부, 수사 단계 대응"                # 목록용 짧은 제목
result: "기소유예"                                       # 결과 배지
category: "형사"                    # 형사 | 민사 | 가사 | 부동산·건설 | 기업 | 기타
date: "2026-07-19"                  # 목록 정렬용 (표시는 선택)
judgment: "./judgment-masked.pdf"   # 없으면 필드 생략
---
(HTML 본문 — 신규는 구조화 조각, 기존은 <p> 나열)
```

- 정적 생성(generateStaticParams). PDF는 정적 자산으로 서빙되어 직접 URL을 갖는다
  (`/cases/{slug}/judgment-masked.pdf` 형태 — 빌드 산출 경로에 맞게).

## [작업 2] 기존 39건 마이그레이션 (일회성 스크립트)

1. Supabase `success_cases` 전 행 조회 → 행마다:
   - slug 생성: title 기반 영문 소문자-하이픈 (중복 시 `-2` 접미). **id 숫자를
     slug로 쓰지 않는다**
   - `description`(HTML) → index.md 본문으로 그대로 (기존 `<p>` 구조 유지 —
     신규 구조로 재작성하지 않는다)
   - `judgment_url`(Base64) → 디코딩해 `judgment-masked.pdf` 파일로 복원.
     복원 후 PDF 열림 검증(파일 시그니처 %PDF 확인)
   - title/result/category/created_at → frontmatter (list_title은 title 축약으로
     임시 생성 — 20자 내외, 추후 사용자가 다듬을 수 있게 목록 보고)
2. 마이그레이션 결과 보고: 총 건수 / PDF 복원 성공·실패 목록 / slug 목록.
   **실패 건이 있으면 DB 제거 전에 반드시 사용자 확인.**
3. 검증 완료 후: success_cases 조회 코드 제거. 테이블 자체는 백업 성격으로
   당분간 유지(삭제하지 않음 — 사용자가 별도 지시할 때까지).
4. 리다이렉트 불요 (임시 도메인 — 색인 자산 없음, 기존 원칙과 동일).

## [작업 3] 목록 페이지

- 현행 성공사례 목록 UI 유지하되 데이터 소스만 frontmatter 빌드 기반으로 교체
- 카드 표시: **list_title** + result 배지 + category. 본문 발췌를 쓰고 있다면
  신규 구조 본문에서는 `.case-stage` 첫 문단부터 발췌 (`.case-brief`의 `<dl>`
  텍스트가 섞이면 안 됨)
- 분야 필터: category 기준 (글 없는 분야 자동 숨김 — 기존 원칙 유지)

## [작업 4] 상세 페이지 템플릿

case-detail-preview.html을 그대로 재현:

1. 배지(result 네이비 / category 연회색) + 제목
2. 본문 렌더 — 신규 구조 클래스 스타일:
   `.case-brief`(dl 그리드, 상단 2px 네이비) / `.case-stage` + `.stage-label`
   (골드 라벨) / `.case-issue`(복합 사례 쟁점 블록 — 좌측 2px #e0d9c8 보더,
   preview 스타일) / `.case-diagram`(관계도 컨테이너 — 보더 박스, 내부 인라인 SVG는
   본문에 포함되어 옴) / `.case-chronology`(사실관계 연표 2열 표 — preview 스타일) / `.case-timeline`(진행 경과 목록 — preview 스타일) / `.case-result`(네이비 좌보더 박스) / `.case-caveat`(회색
   유의점) / `.case-notice`(고지)
3. **기존 `<p>` 나열 본문과 공존**: 클래스 스코프 스타일이라 기존 본문 렌더에
   영향 없어야 한다. 기존 사례 1건 + 신규 구조 1건(더미) 나란히 회귀 확인
4. **문서 카드** (frontmatter `judgment` 존재 시):
   - preview의 `.doc-card` 스타일 — PDF 아이콘 + "이 사건의 처분 문서" +
     "개인정보 마스킹본 · PDF · 클릭하면 화면에서 바로 열립니다"
   - 클릭 → **페이지 내 라이트박스 오버레이**로 PDF 표시 (iframe/embed, 어두운
     배경, ✕·ESC·배경 클릭으로 닫힘 — 사례 페이지로 복귀)
   - 모바일(뷰포트 <768px 또는 인라인 렌더 불가 환경): 오버레이 대신 **새 탭
     열기 폴백** — 모바일 브라우저의 PDF 인라인 렌더가 불안정하기 때문
   - `judgment` 없는 사례는 카드 미표시

## [작업 6] 기존 사례 재생산 — 순차 (일괄 배치 아님)

기존 39건은 작업 2의 이사(형식 그대로 이관)로 사이트에 계속 게시된 상태를
유지한다. 재생산은 **별도 일괄 프로젝트가 아니라 신규 사례 발행과 같은 플로우**로,
사용자가 원하는 사례부터 하나씩 진행한다 (success-case-writer 스킬 사용,
원본 판결문 입력 + 기존 본문 보조 참고).

발행 큐 우선순위 (사이트 전략):
1. **신규 분야 사례 우선** — 건설·부동산·민사·가사 (현재 사례가 전부 형사라
   창끝 분야 증거가 0건인 것이 최대 공백)
2. 기존 형사 재생산은 후순위·수시 — 이미 게시 중이므로 급하지 않다. 품질이 아쉬운
   것, 대표로 노출할 것부터 선별

기존 사례를 재생산할 때의 추가 규칙 (신규 작성 규칙에 더하여):
- **slug·date 유지** — 같은 폴더의 index.md 본문과 frontmatter(list_title 등)만
  교체. URL이 바뀌지 않는다
- 소스 우선순위: 판결문 > 기존 본문(의뢰인 상황·수임 경위 등 맥락). 충돌 시
  판결문이 이기고 충돌 내역 보고
- 검증: 결과 배지=본문=제목=판결문 주문 일치
- **마스킹 재점검**: 그 사례의 기존 마스킹 PDF를 원본과 대조, 미흡 시 재마스킹
  (masking-guide 절차·평면화) 후 교체
- 원본 판결문은 저장소 트리 밖 경로에서만 접근, 절대 커밋 금지
